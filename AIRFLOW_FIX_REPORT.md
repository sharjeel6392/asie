# ASIE Airflow DAG Failure - Root Cause & Solution

## 📋 Executive Summary

**Problem**: The `retrain_pipeline` task in the ASIE Airflow DAG was failing silently with "zombie job" detection after ~9 seconds of execution.

**Root Cause**: MLflow SQLite database schema was corrupted/out-of-sync with the installed MLflow version (3.2.0), causing Alembic migration errors.

**Error Message**: 
```
"Can't locate revision identified by 'd3e4f5a6b7c8'"
```

**Solution**: Delete and recreate the MLflow database.

---

- ❌ `retrain_pipeline` task: FAILED with "zombie job" detection
- Task ran for ~9 seconds then terminated with exit code 1
- No Python traceback visible in Airflow logs

## ✅ Solution Implemented

### Step 1: Delete Corrupted Database
```bash
rm /home/kirksalvator/mlflow.db
```

**Result**: MLflow creates a fresh database with correct schema on next run
- Database size: 552 KB → Fresh (Alembic creates from scratch)
- All 50+ Alembic migrations run successfully
- Schema now synced with MLflow 3.2.0

### Step 2: Improve DAG Logging
Updated [airflow-home/dags/retraining_dag.py](../airflow-home/dags/retraining_dag.py):
- Added comprehensive logging around `run_retraining()` function
- Better error messages with visual separators
- Logs drift check result
- Logs config being used
- Improved exception handling and reporting

### Step 3: Airflow Logging Recursion Fix
A second issue appeared after the MLflow database fix: Airflow task logs were entering a recursive loop through `airflow.utils.log.logging_mixin.StreamLogWriter` when `logging.lastResort` wrote into a wrapped STDERR stream.

- `logging.lastResort` was being routed to a wrapped `sys.stderr` object inside Airflow, which re-entered Airflow logging and caused `RecursionError`.
- The live scheduler/webserver run produced repeated recursion traces and zombie task detection, even though isolated `airflow tasks test ...` could complete once the underlying task code was healthy.

Fix implemented:
- Added `airflow-home/airflow_local_settings.py` to set `logging.lastResort` to a standard `StreamHandler` on `sys.__stderr__` during Airflow startup.
- Patched Airflow's `airflow/utils/log/logging_mixin.py` to add a reentrancy guard inside `StreamLogWriter._propagate_log()`. If the writer is already propagating, it now writes directly to `sys.__stderr__` instead of re-entering the logging system.

Result: live Airflow execution no longer triggers recursive logging cycles, and the retraining DAG can run without the previous `RecursionError` loop.
